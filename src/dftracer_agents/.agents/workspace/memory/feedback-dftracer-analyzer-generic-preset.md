When `analyze()`/`diagnose()` return empty/zero results against real trace data, root-cause and fix the TOOL, don't just fall back to manual parsing and move on.

**Why:** during a PECAN session, `analyze(analyzer_preset="posix")` and `analyzer_preset="dlio"` both silently returned 0-row flat views / empty Layer Breakdown (returncode=0, no error) against a trace with 130M+ real events, because the app's `dft_event_logging` custom categories (`compute`/`preprocess`/`communication-io`) don't match either preset's hardcoded layer-name list. `diagnose()` separately returned "0 metric observations" due to THREE compounding bugs: (a) `_diagnose_via_api` always no-op'd because it checked for a `diagnose_checkpoint` method an outdated `dfdiagnoser` release didn't have, (b) a cascade-logic bug masked the real API exception behind a generic CLI error, (c) `Diagnoser.diagnose_checkpoint` transitively imports `dask_jobqueue`, which calls `signal.signal()` at MODULE IMPORT TIME — crashing on the MCP server's worker thread (`ValueError: signal only works in main thread`) the FIRST time any tool call triggered that import chain.

**How to apply:** the user explicitly directed "fix it in the actual tool, don't route around it" when I initially proposed lowering `cluster_n_workers` as a workaround for the RocksDB race. Fixed for real: (1) `dftracer-analyzer` package upgraded (shared MCP venv) to a release with `AnalyzerPresetConfigGeneric` (`auto_layers_by_category=True`, no hardcoded layer names) — now the MCP `analyze` tool's default preset; (2) `dfdiagnoser` upgraded to a release with real `diagnose_checkpoint`; (3) `_diagnose_via_api` rewritten to actually call it and convert `DiagnosisFinding` objects properly; (4) an eager `import dftracer.analyzer.fact_engine` added at MODULE LOAD time (not lazily inside a tool call) to dodge the signal-handler thread crash; (5) `_ensure_analyzable_path` now auto-builds the RocksDB index single-threaded before any multi-worker `analyze()` call. All confirmed installing/upgrading a package into the SHARED MCP server venv (not just the session-local venv) requires explicit user confirmation each time — even a strong contextual signal ("here's the repo, do the fix") from the user in one turn is NOT blanket consent for a later, different shared-venv install; ask again. See [[dftracer-diagnoser]] skill rules.md/pitfalls.md for the full technical writeup, already synced to all 3 harnesses via `agents_sync`.
