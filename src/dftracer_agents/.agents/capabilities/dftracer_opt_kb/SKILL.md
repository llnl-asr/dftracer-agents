# dftracer_opt_kb

An optimization study is only worth its cost if the next study starts from it. Findings belong to three
scopes, and conflating them is what makes them unreusable:

| Scope | Level | Transfers to |
| --- | --- | --- |
| system | L3 | any workload **on that system** (and to no workload off it) |
| software | L2 | any workload **linking that software**, any system |
| workload | L1 | that application, **any system** |

The KB is append-only JSONL at `<workspaces>/_memory/optimization_kb.jsonl` (`DFTRACER_WORKSPACES`,
default `workspaces` relative to the server's cwd). `opt_kb_render` regenerates the dftracer-agents
`dftracer-optimization-kb` skill files (system.md, software.md, workload.md) from it; the reference
tables at the end of this skill are the content of those files at conversion time (27 system, 41
software, 69 workload entries). The per-session strategy memory (`session_memory_*`) is a separate
store of strategy outcomes per metric and system context.

## Rules
1. **Recall precedes proposal.** Step 1 of every optimization loop is `opt_kb_lookup(system=...,
   workload=..., software=..., scope=..., metric_scope=...)`, before generating any proposal; carry the
   results into the proposal table's "prior result" column and read each row's `notes` (that is where
   caveats like "accepted but ignored" live).
2. Record only **measured** results: `metric`, `before`, `after` are required. A proposal is a
   hypothesis, not an entry. Record failures and no-ops too: knowing a lever did nothing is a result
   ("cb_nodes=8 was accepted but changed nothing" saves the next run an iteration).
3. Every entry carries a **citation**: paper (arXiv/DOI/ACM/IEEE/USENIX, preferred) > official docs >
   web page > `session:<run_id>` (an in-house measurement, marked so it is never mistaken for external
   evidence). Use `citation_type` to override the URL heuristic when it misreads a source (a project page
   is documentation even when its hostname says otherwise).
4. Apply optimizations **one at a time** and measure each, or the attribution is worthless.
5. Pick `scope` honestly: true of the machine/hardware -> `system` (needs `system`); true of the
   library/runtime -> `software`; true of the application -> `workload` (needs `workload`).
6. `metric_scope` is a second, orthogonal axis: `app` (default; the app's own trace: epoch/I-O time,
   app-observed bandwidth) or `system` (a filesystem/system-level outcome: aggregate achieved bandwidth,
   reduced filesystem load; currently a trace-derived proxy, not OST/MDT-side telemetry). An L3 change can
   still target an app metric.
7. **Non-degradation guard (MANDATORY):** a `metric_scope="system"` entry MUST carry the paired
   `app_metric`/`app_before`/`app_after` (`opt_kb_record` rejects one without it). If the paired app metric
   regressed more than 2.0%, the verdict is forced to `regression` (`guard_triggered: true`) however good
   the system number looks: never apply/keep such a change.
8. Verdicts: `win` at >= +5%, `regression` at <= -5%, else `no_change` (`delta_pct` positive always means
   better; `lower_is_better` False for bandwidth).
9. `before`/`after` are medians (p50) over >= 5 replicates; `notes` carries the p95/min/max band and the
   replicate count, and "literature-pass finding, not diagnosis-ranked" when it came from the literature pass.
10. `opt_proposal_table`: every row needs a citation (uncited rows are rejected, not rendered) and the
    POTENTIAL `app_impact_pct`/`system_impact_pct` (0, never missing, for N/A); rows sort by
    0.5*app + 0.5*system, citation quality breaks ties. Once applied and measured, fill
    `actual_app_impact_pct`/`actual_system_impact_pct` next to the potential numbers (never overwrite).
    Every considered candidate stays in the table with `status` applied/not-applied/deferred and a
    `skip_reason`. Apply one row at a time in table order, measure, `opt_kb_record`, then re-rank against
    the post-apply diagnosis. After the table is done, re-diagnose a fresh trace, report whether the
    ranking shifted and the next round's ceiling, and ask the user before another pass: never loop
    automatically.
11. After recording, `opt_kb_render()` so sessions that never call the tools inherit the knowledge.
12. Last step: validate entries with `dftracer_opt_kb_check(entry_json=...)` before `opt_kb_record`, and
    audit the store with `dftracer_opt_kb_check(kb_file=...)`.

## Constraints
- Never hand-edit the rendered markdown; record with `opt_kb_record`.
- Never record an unmeasured proposal, a bundled multi-lever change, or a system win whose guard fired as a win.
- Redact before you persist: no usernames, user paths, job ids or hostnames in `change`/`notes`
  (citations are exempt).

## Corner cases
- A KB "win" can be a retraction: the BERT entry shows an apparent 71%-of-wall metadata bottleneck was a
  one-off transient Lustre stall; re-measure an alleged bottleneck on a fresh replicate before crediting
  or optimizing it.
- Superseding entries: re-measured results (fresh output dir per replicate, interleaved arms) supersede
  earlier same-dir or order-alternated entries; the newer `change` text says so. Read both.
- `software` scope may name several libraries (`"hdf5,mpi-io,lustre"`); lookup matches any of them, so a
  finding about MPI-IO surfaces for a session that uses HDF5 on top of it.
- A corrupt JSONL line is skipped by the lookup (it must not sink the whole KB); the validator reports it.

## Parallel plan

Independent calls go out together in one message: predictor calls on different inputs, and lookups such as knowledge_search or lesson_search, do not depend on each other. Sequential, and why: the validator runs after the predictor whose result it rules on, and the corrector only after the validator's verdict. Larger fan-outs build on [[tools_parallel]] (parallel_plan / parallel_call / parallel_validate).

## Corrector
`dftracer_opt_kb_check` reports these checks; repair the entry (or the store), validate again, then
`opt_kb_record`. The same failure twice stops for the user.
- entry_parse: pass the entry or list as JSON text (or a path to a JSON file).
- kb_file_exists: pass `<workspaces>/_memory/optimization_kb.jsonl` of the right workspaces root.
- kb_file_parses: repair or remove the corrupt lines it names.
- entries_valid: per entry it names: an invalid scope -> workload/software/system (L1/L2/L3); no or
  unusable citation -> find one with [[dftracer_papers]] or use `session:<run_id>`; a system/workload
  scope without `system`/`workload`; no `change`/`metric`; `before`/`after` not numbers -> measure first;
  metric_scope=system without the paired app metric -> measure the app metric of the same change; a
  stored verdict that disagrees with the numbers -> re-record (the tool computes it); a `session:`
  citation naming another run -> cite the run that measured it.

## Self-heal
- If a tool here is wrong (classifier, verdict thresholds), capability_update it; do not hand-edit the store.

## Self-learn
- What is explored here becomes a capability: see capability_builder. Every measured result becomes a KB
  entry; a scoped fact that keeps recurring (e.g. a system quirk) also becomes a lesson of that
  system/software/workload capability.

## What works
- 2026-07-08 (tuolumne, h5bench/Flash-X, Lustre + Cray MPICH): `MPICH_MPIIO_HINTS="*:romio_cb_write=enable:cb_nodes=16"`
  + `CRAY_CB_NODES_MULTIPLIER=2` + `lfs setstripe -c 16 -S 4M` on a fresh output dir: POSIX aggregate
  bandwidth 325.94 -> 1924.71 MB/s (+490.5%, 768 ranks); Flash-X critical-path write 5.53 -> 1.45 s.
- `FI_CXI_RDZV_THRESHOLD=16384` on top of that: 1924.71 -> 3238.05 MB/s (+68.2%).
- Megatron-DeepSpeed BERT: aws-ofi-rccl plugin dir on `LD_LIBRARY_PATH` (do not set `NCCL_NET`): train
  step total 177.92 -> 100.78 s (+43.4%).
- See the reference tables below for every measured result, including the no-ops and regressions.
